# Windows 分发方案决策

状态：`spike / 未承诺安装器`
日期：2026-08-24

## 当前结论

第一版正式分发采用“文档化 Node.js 24 + Next standalone 目录”的最小支持路径，不在本阶段引入 Electron 或 Tauri。原因是当前产品是私人、单作者、Windows 本地工具，核心风险在 SQLite 数据恢复与模型配置，而不是窗口壳；先保证数据生命周期，再决定是否需要原生壳和安装器。

## 方案比较

| 方案 | 优点 | 风险/成本 | 当前结论 |
| --- | --- | --- | --- |
| Node 24 + standalone | 变更最小、可复用现有构建、better-sqlite3 兼容路径清晰、易回滚 | 需要用户安装 Node、没有原生托盘/自动更新 | **首选 spike 路线** |
| Electron 包装 | 可提供单文件体验、原生窗口和后续托盘能力 | 体积大、需要处理 server 生命周期、原生模块 rebuild、签名和升级回滚 | 暂不引入 |
| Tauri/native | 包体更小、原生体验好 | 需要额外 Rust/前端桥接、SQLite/native 模块与数据迁移验证 | 暂不引入 |

## 必须实测的证据

1. 干净 Windows 账户安装 Node 24 后能启动 standalone 服务。
2. `better-sqlite3` 原生模块在目标 Node 24 与目标 Windows 架构可加载。
3. 数据库和备份位于安装目录之外，升级或卸载不删除数据。
4. `.env.local`/模型密钥不打进安装产物，启动日志不打印密钥。
5. 升级失败时旧安装目录和数据目录仍可回滚/保留。
6. `scripts/package-smoke.ps1 -Mode DryRun` 不执行安装或删除动作；真实 smoke 只能在明确创建的临时根目录内操作。

## 暂不承诺

在完成真实 Windows 账户、签名证书、原生模块和升级回滚测试前，README 不承诺“一键安装”、自动更新、代码签名或公开部署安全性。
